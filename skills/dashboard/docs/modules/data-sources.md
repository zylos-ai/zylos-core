# Data Sources

## Module Responsibilities

Dashboard collects authoritative session state from Zylos Core, local runtime metrics, and read-only business data, stores them in its own database, and presents them through APIs, SSE, and pages. The current implementation is not a general-purpose Adapter/OTel platform; specific collectors and readers in the code explicitly define its data entry points.

## Current State and Usage

`src/lib/core-state.js` uses Core's `session-state-reader.js` to read the identity, state, active tools, context usage, and account usage of the current Origin (the current session in single-session mode). This path is the authoritative source for the page's current state, context, and rate limits, and refreshes every second by default.

Dashboard no longer infers current session state through its own runtime hooks. Core publishes session state and activity hooks; the upgrade process removes old Dashboard hooks.

## Collectors

| Collector | Data source | Main purpose | Runtime |
|---|---|---|---|
| `PM2Collector` | PM2 process list | Service state, CPU, memory, restart count | All |
| `SystemCollector` | Local system samples | CPU, memory, disk | All |
| `StatuslineCollector` | Core session state (session-state-reader) and account usage | Context, cost, cache, rate limits | All |
| `ConversationCollector` | Claude conversation JSONL | Tokens, cost, tool and session history | Claude |
| `CodexRolloutCollector` | Codex rollout JSONL | Tokens, context, turn and tool history | Codex |

Collectors write normalized samples to `dashboard.db`. When pages display metrics, `MetricResolver` selects samples according to fixed source chains, runtime, and freshness; see [Metric Model](metric-model.md).

## Other Read-Only Sources

- `CoreLogImporter` imports diagnostic/history JSONL generated by Core for history and troubleshooting; it does not replace live state from `CoreState`.
- `C4Reader` reads communication data without writing it, for message statistics and communication views.
- The Scheduler reader reads scheduling data without writing it, for task state and history views.
- Dashboard's own database stores collected metrics, events, and records needed for aggregation; see [Database Maintenance](db-maintenance.md).

## Hook Boundaries

The repository retains migration compatibility code and test fixtures such as `hook-installer.js` and `hook-ingest.cjs`, but the current production entry point does not instantiate the Dashboard hook installer. Core manages runtime hook installation, upgrades, and ownership; do not configure Dashboard as an independent hook owner.

## Security Boundaries

- External databases are accessed read-only; Dashboard writes only to its own data directory and database.
- APIs expose only the state, counts, timestamps, and sanitized events needed for display, never prompts, message bodies, environment variables, or raw tool inputs.
- A collector failure should degrade only that source, without interrupting other collectors or modifying upstream data.
